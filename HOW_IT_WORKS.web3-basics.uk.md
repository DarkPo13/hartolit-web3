# Web3 у цьому проєкті: простими словами для розробника

Цей документ для розробника, який добре знає звичайну веб-розробку (сервер, БД, S3, HTTP API, Docker), але ніколи не працював з Web3. Кожне Web3-поняття тут пояснено через знайомі речі з Web2. Технічні деталі нашої реалізації описано в [HOW_IT_WORKS.dev.uk.md](HOW_IT_WORKS.dev.uk.md); спершу прочитайте цей документ, потім той.

---

## 1. Головна картина

Hartolit складається з трьох «світів»:

```
┌─────────────── 1. НАШ ЗВИЧАЙНИЙ WEB2 ───────────────┐
│ Next.js-сервер, PostgreSQL, S3-бакет, ClamAV, пошта  │   ← приватне, наше, як у будь-якому SaaS
└──────────────────────────────────────────────────────┘
           │ кладе публічний JSON          │ читає (лише читає!)
           ▼                               ▼
┌──── 2. IPFS ────────────────┐  ┌──── 3. БЛОКЧЕЙН BSC ──────────────────┐
│ мережа файлового обміну,    │  │ одна спільна база даних, копію якої   │
│ де файл шукають за його     │  │ тримають сотні комп'ютерів у світі;   │
│ відбитком (як торенти)      │  │ рядки в ній змінюють лише за          │
│                             │  │ правилами програми (смарт-контракту)  │
│ тут лежить: публічний JSON  │  │ тут лежить: відбиток JSON і посилання │
└─────────────────────────────┘  └───────────────────────────────────────┘
                                          ▲
                                          │ підписана транзакція
                              MetaMask у браузері адміна (ключ лише там)
```

**Навіщо три світи, а не лише наша БД?** Якщо все лежить у нашій БД, перевіряльник мусить вірити нам на слово: ми можемо тихо змінити рядок. Блокчейн ніхто не може переписати, навіть ми. Проте зберігати в ньому дорого, тому туди кладемо лише 32-байтовий відбиток. Сам документ кладемо в IPFS, де його адреса і є його відбитком. Перевіряльник бере документ з IPFS, рахує відбиток і порівнює з блокчейном. Нам довіряти не треба.

### Словничок «Web2 ↔ Web3»

| Web3-поняття | Найближчий аналог з Web2 | Головна різниця |
|---|---|---|
| IPFS | BitTorrent / S3 | файл адресується відбитком вмісту, а не назвою |
| Kubo | MinIO (сервер S3) чи Postfix (поштовий сервер) | програма, яка «говорить» протоколом IPFS |
| Вузол IPFS (node) | запущений сервер MinIO | один запущений Kubo |
| CID | magnet-посилання торента / ETag в S3 | є одночасно адресою й відбитком |
| Блок IPFS | об'єкт у бакеті | його ключ не вибирають, його рахують з вмісту |
| Pin | «не видаляти» / виняток із lifecycle-правила | без pin вузол може прибрати блок під час чистки |
| Шлюз (gateway) | публічний URL бакета / CDN | HTTP-доступ на читання: `/ipfs/{cid}` |
| RPC вузла IPFS | S3 API з ключами доступу | адміністративний API: записати, закріпити |
| Блокчейн | git-репозиторій, який клонували тисячі людей, або одна спільна реплікована БД | історію неможливо тихо переписати |
| Блок блокчейну | коміт у git | містить хеш попереднього, тому ланцюжок «зшитий» |
| Смарт-контракт | збережена процедура разом зі своїми таблицями | код після розгортання змінити неможливо |
| Транзакція | підписаний запит `UPDATE` до спільної БД | платна (газ), незворотна |
| Гаманець і ключ | SSH-ключ | приватна частина лише у власника; адреса — похідна від публічної |
| MetaMask | ssh-agent у браузері | зберігає ключ і підписує |
| RPC блокчейну | рядок підключення до чужої репліки БД | HTTP POST з JSON |
| viem | драйвер `pg` / SDK | бібліотека для читання блокчейну й кодування викликів |
| wagmi | React-хуки над viem | для роботи з гаманцем у браузері |
| Токен ERC-721 (NFT) | рядок у таблиці контракту | «ERC-721» — загальноприйнятий інтерфейс, як OpenAPI-специфікація |
| Testnet / Mainnet | staging / production усього світу | у Testnet монети безкоштовні й нічого не варті |

## 2. Байти: звідки вони беруться

Будь-які дані в комп'ютері — це послідовність байтів (чисел від 0 до 255). Текст перетворюється на байти за кодуванням UTF-8:

```
текст:  {"area":12.5}
байти:  7b 22 61 72 65 61 22 3a 31 32 2e 35 7d        (13 байтів, у hex)
        {  "  a  r  e  a  "  :  1  2  .  5  }
```

Латинська літера займає 1 байт, кирилична — 2:

```
текст:  Київ
байти:  d0 9a  d0 b8  d1 97  d0 b2                    (8 байтів)
         К      и      ї      в
```

**Хто генерує байти публічного паспорта:** наш сервер, звичайним кодом TypeScript. Жодної Web3-магії тут немає:

```ts
const snapshot = { schemaName: "...", farm: { label: "Fictional Testnet Farm" }, /* ... */ }; // об'єкт з БД, лише дозволені поля
const canonicalJson = canonicalize(snapshot);         // рядок JSON: ключі відсортовані, без пробілів
const bytes = new TextEncoder().encode(canonicalJson); // рядок → байти UTF-8
```

Ці байти потім:

- хешуються;
- надсилаються в IPFS;
- їхній хеш записується в блокчейн.

Чому ключі сортуються (`canonicalize`): `{"a":1,"b":2}` і `{"b":2,"a":1}` для людини однакові, а байти в них різні, тож і відбитки різні. Сортування гарантує, що ті самі дані завжди дають ті самі байти.

## 3. Хеш (SHA-256): відбиток байтів

Хеш-функція — звичайна функція зі стандартної бібліотеки (у Node — модуль `crypto`, у браузері — `crypto.subtle`). На вхід вона бере будь-які байти, на вихід віддає рівно 32 байти. У hex це 64 символи.

```ts
import { createHash } from "node:crypto";
createHash("sha256").update('{"area":12.5}').digest("hex");
// e092721ef7dfca8d3fbacf5cdcd6da5c3ab8fb52add777d40a77aebc6dcae9e9
```

- Ті самі байти завжди дають той самий хеш, на будь-якому комп'ютері й будь-якою мовою.
- Змініть один символ (`12.5` → `13`), і хеш стане зовсім іншим.
- З хеша неможливо відновити дані, але легко перевірити, чи дані йому відповідають.

Знайома аналогія: S3 рахує для кожного об'єкта **ETag** (зазвичай MD5 вмісту), щоб ви могли перевірити, що файл не пошкоджено. SHA-256 — той самий прийом, тільки надійніший.

## 4. IPFS: що це насправді

### 4.1. Не фреймворк, не база даних і не компанія

**IPFS — це протокол, тобто набір правил, як комп'ютери обмінюються файлами, і мережа комп'ютерів, які за цими правилами працюють.**

Найкраща аналогія — **електронна пошта**:

| Пошта | IPFS |
|---|---|
| SMTP — протокол | IPFS — протокол |
| Postfix, Exchange — програми-сервери | **Kubo** — програма-сервер (написана на Go; є й інші реалізації) |
| ваш поштовий сервер | **ваш вузол** — запущений Kubo |
| можна тримати свій сервер або взяти Gmail | можна тримати свій вузол або орендувати в провайдера (Pinata, Filebase тощо) |

Друга аналогія — **BitTorrent**. Файл ідентифікується хешем (magnet-посиланням). Хто має файл, той його роздає. Якщо жоден «сід» не в мережі, файл недоступний, хоча посилання на нього ніхто не скасовував.

### 4.2. Де фізично лежать дані

**На диску комп'ютера, де запущено Kubo.** У нас локально це Docker-контейнер `ipfs/kubo:v0.43.1` (профіль `ipfs-node` у `compose.yaml`), а дані в Docker-томі `hartolit_ipfs_data` (усередині контейнера `/data/ipfs`). Тобто це наш сервер, наш диск і наш процес, приблизно як MinIO замість AWS S3.

Різниця з S3 у тому, що наш вузол **підключений до світової мережі IPFS**. Будь-який інший вузол у світі може попросити в нього блок за CID і отримати його. Якщо інші вузли теж закріплять (pin) наш блок, з'являться копії. Якщо наш вузол вимкнеться і копій ніде немає, дані стануть недоступними. CID при цьому не зміниться і не «зламається»: він і далі гарантує, що будь-яка знайдена копія справжня.

Саме тому зараз токен №1 відкривається лише на нашому комп'ютері. Наш Kubo працює вдома за роутером, інші вузли до нього не достукуються, і публічні шлюзи (ipfs.io) відповідають помилкою.

**Що означає «покласти в IPFS», якщо IPFS — лише протокол.** Це скорочення, як «надіслати поштою»: пошта — це правила, а лист фізично лежить на конкретному сервері. «Покласти в IPFS» означає записати блок на диск **конкретного вузла** (у нас — нашого Kubo) і роздавати його за правилами IPFS. «В IPFS усе публічне» означає інше: **протокол не має паролів і прав доступу**. Вузол віддає блок кожному, хто назве CID, і не питає, хто той і чи має право. Тому покласти щось на свій вузол IPFS — це як викласти файл на свій сервер без пароля і з відкритими дверима. Диск наш, але прочитати може будь-хто, і будь-хто може зберегти собі копію. Технічно можна зібрати закриту мережу з кількох своїх вузлів (private swarm), але тоді її не бачать ні публічні шлюзи, ні сторонній перевіряльник. А публічна перевірка — саме те, навіщо нам IPFS.

### 4.3. IPFS проти S3

| | AWS S3 | IPFS |
|---|---|---|
| Хто зберігає | Amazon | ті, хто запустив вузол і закріпив блок: ми, провайдер, будь-хто |
| Адреса файла | `bucket/key`, ключ вибираєте ви | **CID** рахується з вмісту, вибрати його не можна |
| Змінити файл за тією ж адресою | можна | **неможливо**: новий вміст означає новий CID |
| Приватність | бакет може бути приватним, є ключі доступу | **прав доступу немає**: вузол віддає блок кожному, хто знає CID |
| Видалити | можна | лише зі своїх вузлів; чужі копії лишаться |
| Плата | за обсяг і запити | за свій сервер або тариф провайдера |

Звідси два правила проєкту:

- у IPFS іде **лише публічний** JSON;
- приватні файли (накладні, метеодані) лежать у звичайному приватному S3.

## 5. Блок, CID, pin: на одному прикладі

Візьмемо байти `{"area":12.5}`.

**Блок** — це просто шматок байтів, який зберігає вузол. У нас один паспорт дорівнює одному блоку: наш JSON займає сотні байтів, а ліміт блоку — 64 КіБ. Великі файли IPFS ріже на багато блоків, але ми цим не користуємося.

**CID** — назва блоку, обчислена з його вмісту:

```
1. SHA-256 байтів           = e092721e…e9e9  (32 байти)
2. дописати спереду 4 байти: 01 55 12 20
                              │  │  │  └─ довжина хеша = 32
                              │  │  └──── хеш-функція = sha2-256
                              │  └─────── формат = raw (просто байти)
                              └────────── версія CID = 1
3. закодувати в base32 і дописати спереду літеру "b"
   = bafkreihasjzb5567zkgt7owpltonnws4hk4pwuvn2535ictxv26g3sxj5e
```

Префікс однаковий для всіх наших даних, тож кожен наш CID починається з `bafkrei`. Решта рядка — це той самий SHA-256, лише записаний літерами. **CID і хеш — одне й те саме число у двох записах**, тому з хеша в блокчейні можна вивести CID, а з CID — хеш. Код цього обчислення займає 20 рядків: [lib/publication/raw-cid.ts](lib/publication/raw-cid.ts).

**Pin** — позначка «зберігати завжди». Kubo вміє чистити диск від блоків, які лише колись проходили через нього (кеш): вручну командою `ipfs repo gc` або автоматично, якщо це ввімкнено. Закріплені блоки чистка не чіпає. Ми кладемо блок одразу з `pin=true`, а потім перевіряємо, що pin справді стоїть.

## 6. Kubo: три порти, три ролі

Запущений Kubo відкриває три порти. Це ключ до розуміння «куди ми підключаємося»:

| Порт | Назва | Хто ним користується | Що робить | Відкривати в інтернет? |
|---|---|---|---|---|
| **4001** | swarm (P2P) | інші вузли IPFS у світі | обмін блоками між вузлами | **так**, інакше світ нас не бачить |
| **5001** | RPC API | **лише наш сервер** | записати блок, закріпити, перелічити pin-и; повний контроль над вузлом | **ніколи**, лише в приватній мережі або за паролем/токеном |
| **8080** (у нас на хості 8088) | шлюз (gateway) | будь-хто через браузер чи HTTP | віддати блок за CID: `GET /ipfs/{cid}` | так, це публічне читання |

Що наш сервер реально надсилає у Kubo. Це звичайні HTTP-запити:

```bash
# Записати й закріпити блок (порт 5001, RPC)
curl -X POST -F "file=@public-snapshot.json" \
  "http://127.0.0.1:5001/api/v0/block/put?cid-codec=raw&mhtype=sha2-256&mhlen=32&pin=true"
# відповідь: {"Key":"bafkrei…","Size":13}

# Перевірити, що закріплено (порт 5001, RPC)
curl -X POST "http://127.0.0.1:5001/api/v0/pin/ls?arg=bafkrei…&type=recursive"

# Прочитати назад як звичайний відвідувач (шлюз)
curl "http://127.0.0.1:8088/ipfs/bafkrei…?format=raw"
```

Слово **RPC** («віддалений виклик процедури») тут означає просто «HTTP API, через який керують програмою». У Kubo це `/api/v0/...`, у блокчейні — інший API з тією самою назвою (розділ 8).

## 7. Блокчейн: спільна база, яку ніхто не може переписати

### 7.1. Що це

Уявіть **одну базу даних**, повну копію якої тримають сотні комп'ютерів у світі (вузли). Дані в ній змінюються лише так:

1. хтось надсилає **транзакцію** — підписаний запит на зміну;
2. спеціальні вузли (валідатори; у BSC їх кілька десятків) кожні менше ніж секунду збирають транзакції в **блок**;
3. блок містить хеш попереднього блоку, як коміт у git містить хеш батьківського;
4. усі вузли перевіряють блок і додають його у свою копію.

Аналогія з git: це репозиторій, який клонували всі вузли. Переписати старий коміт означає змінити хеші всіх наступних, і кожен вузол одразу побачить розбіжність. Тому історію вважають незмінною.

**BNB Smart Chain (BSC)** — одна з таких мереж. У неї є дві окремі мережі:

- **Mainnet** (chain id 56) — «бойова», зі справжніми грошима;
- **Testnet** (chain id 97) — тренувальна, монети tBNB безкоштовно видає кран.

Ми працюємо лише в Testnet.

### 7.2. Де ця база фізично

На всіх вузлах мережі. Не в нас і не в якоїсь однієї компанії. Нам свій вузол BSC не потрібен: ми підключаємося до чужого через RPC (розділ 8).

### 7.3. Смарт-контракт — це програма разом зі своїми таблицями

Смарт-контракт — це код, який ми написали ([contracts/src/HartolitFieldPassport.sol](contracts/src/HartolitFieldPassport.sol), мова Solidity) і **один раз розгорнули** в мережу. Розгортання — теж транзакція. Після неї в контракту з'явилася адреса `0xf5807a0a…cac5`, приблизно як URL, і з того моменту:

- **код змінити неможливо**, ні нам, ні комусь іншому;
- у контракту є **власні «таблиці»**, і рядки в них змінюються лише через його функції.

Наш контракт фактично тримає таку таблицю:

| tokenId | owner (власник) | payloadHash (відбиток JSON) | tokenURI (де лежить JSON) |
|---|---|---|---|
| 1 | `0xfac7…16f6` | `a499b1d1…e921` | `ipfs://bafkreifetgy5…pjee` |

і одну функцію для запису `mintPassport(власник, відбиток, посилання)`. Вона:

- дозволена лише гаманцю з роллю `MINTER_ROLE`;
- відмовляє, якщо такий відбиток уже записано;
- не дає передати токен іншому власнику.

Читати таблицю може будь-хто і безкоштовно.

### 7.4. Токен, NFT, ERC-721

**Токен** у нашому проєкті — це **рядок у таблиці вище**, і більше нічого. Жодних картинок і «криптовалюти».

**ERC-721** — загальноприйнятий стандарт інтерфейсу, як OpenAPI-специфікація. Він описує, що в контракту мають бути функції `ownerOf(tokenId)`, `tokenURI(tokenId)` тощо. Завдяки цьому BscScan, гаманці й будь-які інструменти розуміють наш контракт, не знаючи нічого про Hartolit. «NFT» — побутова назва таких токенів.

Наші токени **soulbound** («прив'язані до душі»): передати чи продати їх не можна, бо паспорт обробки — не товар.

## 8. RPC блокчейну: як наш сервер «бачить» блокчейн

Щоб прочитати рядок з блокчейну, треба запитати якийсь вузол BSC. Вузли надають **JSON-RPC** — HTTP POST з JSON. Наприклад, номер останнього блоку:

```bash
curl -X POST https://<RPC-адреса> -H "content-type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
# {"jsonrpc":"2.0","id":1,"result":"0x84c8a3e"}     ← номер блоку в hex
```

Прочитати `payloadHash(1)` з нашого контракту — це метод `eth_call` із закодованим викликом функції. Кодувати вручну не треба: це робить бібліотека **viem**, як драйвер `pg` робить SQL-протокол за вас:

```ts
const hash = await client.readContract({ address: CONTRACT, abi, functionName: "payloadHash", args: [1n] });
```

**Чиї це вузли?** Компаній, які надають RPC як послугу: безкоштовні публічні (наприклад, publicnode) або платні з вищими лімітами. Це «рядок підключення до чужої репліки бази». Адреса RPC — це змінна оточення `HARTOLIT_MINT_RPC_URL` чи `HARTOLIT_VERIFY_RPC_URL`.

**Сервер через RPC лише читає.** Записувати в блокчейн може тільки підписана транзакція, а підписати її може лише власник ключа (розділ 9).

## 9. Гаманець, ключ, підпис: найближче до SSH-ключів

- **Приватний ключ** — випадкове 32-байтове число. Хто його має, той володіє гаманцем. Його ніколи нікому не показують.
- **Seed-фраза** (12 слів) — зручний для людини запис, з якого відновлюється ключ.
- **Адреса** (`0xfac7…16f6`) обчислюється з публічної частини ключа. Її показують усім, як публічний SSH-ключ.
- **MetaMask** — розширення браузера, яке зберігає ключ і **підписує** те, що ви підтвердите. Як ssh-agent з вікном «дозволити?».
- **Підпис** — математичний доказ «це підтвердив власник ключа». Перевірити підпис може будь-хто, знаючи лише адресу, а підробити неможливо.

У нашому застосунку гаманець підписує дві різні речі:

| Що | Аналогія | Чи змінює блокчейн | Чи платне |
|---|---|---|---|
| **Повідомлення** («цей гаманець мій») | `ssh -T git@github.com`: довести, що ключ ваш | ні, підпис перевіряє наш сервер | ні |
| **Транзакцію** `mintPassport(...)` | підписаний `UPDATE` до спільної БД | **так**, назавжди | так, газ ≈ 0.0002 tBNB |

**Газ** — плата валідаторам за обробку транзакції. Платить відправник, тобто гаманець видавця.

**Nonce** — порядковий номер транзакції гаманця: 0, 1, 2… Кожен номер можна використати лише раз. Це захищає від випадкового подвійного надсилання.

**Підтвердження** — скільки блоків уже лягло поверх блоку з нашою транзакцією. Перші секунди мережа зрідка «переграє» останні блоки, тому ми чекаємо 6 підтверджень і лише тоді вважаємо запис остаточним.

**Головне правило безпеки проєкту:** ключ живе **лише** в MetaMask адміністратора. Наш сервер ключа не має і нічого не підписує. Навіть якщо сервер зламають, від імені Hartolit у блокчейн нічого не запишуть.

## 10. Що наше, а що ні

| Що | Чиє | Де працює | Що буде, якщо воно впаде |
|---|---|---|---|
| Застосунок Next.js | **наше** | наш сервер (зараз ваш комп'ютер) | сайт недоступний; блокчейн і IPFS не постраждають |
| PostgreSQL | **наше** | наш сервер / керована БД | недоступні робочі процеси; публічна перевірка **працює** без неї |
| S3-бакет із доказами | **наше** (або орендоване, як AWS S3) | хостинг | недоступні файли-докази |
| ClamAV | **наше** | контейнер поруч із застосунком | нові файли не приймаються |
| Вузол IPFS (Kubo) | **наше** (або орендований провайдер) | наш сервер | публічні JSON недоступні, якщо інших копій немає |
| Мережа IPFS (інші вузли, ipfs.io) | **не наше**, нічиє | весь світ | — |
| Код контракту | **написали ми**, але після розгортання він нічий: змінити його не можемо навіть ми | усі вузли BSC | — |
| Мережа BSC | **не наше** (BNB Chain і валідатори) | весь світ | малоймовірно; тоді не працює ні випуск, ні перевірка |
| RPC-провайдер | **не наше**, сервіс | їхні сервери | замінюємо адресу в налаштуваннях на іншу |
| Гаманець видавця (ключ) | **ваш особисто** | MetaMask у вашому браузері | втрачений ключ = втрачене право випускати токени |
| BscScan | **не наше**, «переглядач» блокчейну | testnet.bscscan.com | ні на що не впливає, це лише вітрина |

## 11. Повний шлях одного паспорта: куди йдуть дані

```
 1. Оператор заповнює картку        браузер ──HTTPS──► наш Next.js ──► наша PostgreSQL
 2. Оператор додає PDF               браузер ──HTTPS──► наш S3 напряму; потім Next.js ──► ClamAV
 3. Адмін схвалює                    браузер ──► Next.js ──► PostgreSQL
 4. Адмін підтверджує публічні поля  Next.js будує JSON → байти → SHA-256; зберігає в PostgreSQL
 5. Адмін доводить, що гаманець його MetaMask підписує текст ──► Next.js перевіряє підпис (без блокчейну)
 6. Адмін дає згоду і надсилає       Next.js ──HTTP POST :5001──► наш Kubo: block/put, pin
                                      Kubo зберігає блок на своєму диску і повідомляє мережі IPFS «у мене є bafkrei…»
 7. Сервер перевіряє                 Next.js ──GET шлюз /ipfs/{cid}──► Kubo: байти ті самі? ✅
 8. Сервер готує транзакцію          Next.js ──RPC (читання)──► BSC: контракт той? nonce гаманця?
                                      віддає браузеру: «виклич mintPassport(власник, хеш, ipfs://cid) з nonce N»
 9. Адмін підписує транзакцію        MetaMask ──свій RPC──► мережа BSC → потрапляє в блок
10. Сервер чекає 6 підтверджень      Next.js ──RPC (читання)──► BSC: транзакція є? токен №…? → PUBLISHED
11. Будь-хто сканує QR               телефон ──► /passports/1 на нашому Next.js
                                      Next.js ──RPC──► BSC: payloadHash(1), tokenURI(1)
                                      Next.js ──шлюз──► IPFS: байти за CID
                                      SHA-256(байти) == payloadHash ? «Перевірено» : «Не збігається»
                                      (PostgreSQL для цього не потрібна)
```

Перевірку з кроку 11 може повторити будь-хто й без нашого сайту: взяти хеш з BscScan, байти з будь-якого шлюзу IPFS і порахувати SHA-256. На цьому й тримається довіра до системи.

## 12. Часті запитання

**Чи можна видалити паспорт з IPFS?**
З нашого вузла — так (зняти pin і почистити). З чужих вузлів, які встигли зберегти копію, — ні. Запис у блокчейні з відбитком і посиланням лишиться назавжди. Тому в IPFS іде лише те, що можна показувати завжди.

**Чи може Hartolit змінити вже випущений токен?**
Ні. Контракт не має такої функції, а код контракту змінити неможливо. Можна лише випустити **новий** токен для виправленого запису. Застосунок пов'язує їх як «виправлення».

**Що буде, якщо наш сервер повністю зникне?**
Токени лишаться в блокчейні. Якщо копії JSON є в IPFS (на іншому вузлі чи у провайдера), будь-хто зможе перевірити паспорти й без нас. Приватні дані (БД, S3) доведеться відновлювати з резервних копій.

**Чи платимо ми за блокчейн?**
Лише газ за кожен випуск токена, з гаманця видавця. У Testnet це безкоштовні тестові монети. Читання блокчейну безкоштовне; платити можна хіба за потужніший RPC-тариф.

**Чи потрібен нам свій вузол блокчейну?**
Ні. Достатньо RPC-провайдера. Свій вузол BSC — це сотні гігабайтів даних і окреме обслуговування.

**Чи потрібен нам свій вузол IPFS?**
Потрібен або свій Kubo на сервері, або провайдер із сумісним з Kubo API. Звичайний API Pinata нам не підходить: він рахує CID інакше. Це одне з питань вибору хостингу.

**Чим «блок IPFS» відрізняється від «блоку блокчейну»?**
Нічим, крім слова. Блок IPFS — це шматок даних файла. Блок блокчейну — це пакет транзакцій, що додається до ланцюга. Це дві різні речі з однаковою назвою.

**А «RPC» в IPFS і в блокчейні — одне й те саме?**
Ні. Це просто загальна назва для «API, через яке керують програмою». RPC Kubo — це `/api/v0/...` на нашому вузлі IPFS. RPC блокчейну — це JSON-RPC (`eth_call`, `eth_blockNumber`) на вузлі BSC.
